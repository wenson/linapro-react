# 产品开发流程规则

## 适用范围

本规则约束`lina-tapcanvas`的设计、Tasklist、实施、反馈、阶段记录、审查和交付。产品不使用 OpenSpec；需求和验证事实由设计文档、冻结 Tasklist、阶段执行记录、代码、测试与审查共同承载。

## 权威记录

- 总体架构和专项设计说明目标、边界、契约与取舍。
- 冻结 Tasklist 是实施顺序、任务状态和验收门禁的唯一权威清单。
- 每个阶段必须维护执行记录，包含任务映射、实际命令、退出码、失败项、截图目录、影响评估和审查结论。
- 代码、测试输出和当前工作区状态是实现事实，历史记录不得替代当前验证。
- 继承自 LinaPro 上游的`openspec/`目录、OpenSpec workflow、skill 或 prompt 不属于产品需求、任务、验证或交付证据。

## 执行流程

1. 读取`AGENTS.md`和命中的规则文件，确认授权、范围和禁止修改项。
2. 对多步骤任务维护执行计划；任务语义、顺序或验收发生变化时，先按冻结规则升级 Tasklist 版本。
3. 阶段开始前创建执行记录，并只修改该阶段允许的路径。
4. 实现后运行匹配风险的单元测试、E2E、编译、静态扫描、文件检查或治理验证。
5. 依据当前工作区执行审查，修复阻塞问题后再勾选任务和阶段验收。
6. 未获得用户明确授权时，不执行 commit、push、PR、merge、tag 或发布。

## 反馈处理

- 用户反馈必须先说明根因、处理范围和验证方式，再修改代码或文档。
- 局部反馈直接写入当前阶段执行记录；改变冻结范围、架构、任务顺序或验收标准时，必须新增变更记录并升级 Tasklist 版本。
- 功能行为反馈需要能够复现问题并证明修复的自动化测试；纯治理反馈使用静态扫描、文件检查、格式检查和审查结论。
- 反馈完成前必须评估`i18n`、缓存一致性、数据权限、开发工具跨平台和测试影响；无影响时也要明确记录。

## 阶段记录要求

- 阶段记录使用`docs/2026-07-12-react-workbench-execution-record-template.md`或后续明确替代模板。
- 命令必须记录实际环境变量、代理、参数和退出码。替代验证必须说明原因、覆盖范围和剩余风险。
- 用户可观察 UI 阶段必须记录截图目录和视觉审查；不涉及 UI 时写明不适用原因。
- 阶段状态只有`Not Started`、`In Progress`、`Passed`和`Blocked`。没有验证证据不得标记`Passed`。

## 审查要求

- 审查范围从`git status --short`和未跟踪文件展开开始，包含 staged、unstaged、未跟踪和生成器影响文件。
- 审查必须重新读取`AGENTS.md`和命中的规则文件，不得只依赖历史上下文。
- 发现问题时必须提供路径、行号、严重性、规则依据和建议操作。
- 严重问题阻塞任务和阶段完成；警告必须记录剩余风险和处理决定。
- 审查结论必须列出验证命令，并明确 API、DI、数据库、数据权限、缓存、`i18n`、跨平台和 E2E 是否受影响。
